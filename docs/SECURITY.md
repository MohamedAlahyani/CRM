# Commerce Operations CRM — Security and Privacy

## 1. Security objectives

1. Prevent unauthorized access to employee functions and customer data.
2. Ensure every action is scoped to the authenticated organization and granted permission.
3. Protect provider credentials, session secrets, passwords, and encryption keys.
4. Authenticate all provider webhook sources before processing data.
5. Preserve integrity and traceability of operational state and external side effects.
6. Minimize personal data in storage, logs, diagnostics, and frontend responses.
7. Recover safely from process failure, provider failure, operator error, and infrastructure loss.

Security controls are release requirements, not optional post-launch hardening.

## 2. Trust boundaries and assets

### 2.1 Trust boundaries

- Public internet to reverse proxy/API webhook endpoints.
- Employee browser to web/API.
- API/worker to PostgreSQL and Redis.
- Worker to Shopify, WhatsApp, and future Ozone.
- Runtime to secret injection/key storage.
- Application containers to logging, monitoring, and backup systems.
- Administrative host access to the self-hosted installation.

### 2.2 High-value assets

- Password hashes and active sessions.
- Shopify, Meta, and future Ozone credentials.
- Webhook verification secrets.
- Backup keys and any future field-encryption keys.
- Customer names, phone numbers, email addresses, physical addresses, notes, and order history.
- Order values, operational decisions, shipment/tracking data, and message status.
- Roles/permissions, audit history, outbox operations, and integration diagnostics.

## 3. Threat model

| Threat | Primary controls |
|---|---|
| Credential stuffing/password guessing | Rate limiting, generic errors, Argon2id, monitoring, optional account cooldown |
| Session theft/fixation | High-entropy opaque tokens, rotate on login, hash at rest, Secure/HttpOnly/SameSite cookie, expiry/revocation |
| CSRF | SameSite plus synchronizer/double-submit token and Origin validation for unsafe browser requests |
| Cross-site scripting | React escaping, no unsafe HTML, CSP, output encoding, dependency review |
| Broken access control | API permission guards, mandatory organization context, ownership constraints, negative tests |
| SQL injection | Prisma parameterization, no unreviewed raw SQL, input validation |
| SSRF through provider configuration | Provider endpoints are server-configured allowlisted values; no arbitrary user URL fetch |
| Forged/replayed webhooks | Raw-body signature verification, account binding, event dedupe, timestamp/replay checks where official protocol supports them |
| Duplicate outbound shipment/message | Domain constraints, stable idempotency keys, outbox, operation records, reconciliation |
| Secret/PII leakage | Server-only secrets, encryption, response DTOs, log redaction, payload minimization |
| Queue poisoning/job tampering | Private authenticated Redis, validated versioned job payloads, job IDs, organization checks |
| Malicious file/form payload | MVP avoids file upload; strict DTO size/type limits |
| Dependency/container compromise | Lockfile, scanning, minimal images, non-root runtime, patch process, SBOM/release provenance |
| Database/backup theft | Encryption at rest where host supports it, application field encryption, encrypted backups, least-privilege access |
| Insider misuse | Least privilege, audit, restricted integration/user management, reviewable actions |
| Host compromise | OS hardening, restricted admin access, firewall, secret separation, monitoring, backups; owned by deployment operator |

## 4. Authentication

### 4.1 Password storage

- Hash passwords with Argon2id using the platform library's encoded format.
- Parameters are benchmarked on production-class hardware to target approximately 250–500 ms per verification without exhausting memory under expected concurrency.
- Minimum baseline is recorded in configuration and cannot silently downgrade; OWASP guidance at implementation time is reviewed.
- Use a cryptographically secure random salt generated by the library.
- An optional server-held pepper may be used only with a documented rotation/recovery procedure; it never resides in the database.
- Enforce a minimum length of 12 characters and allow password-manager generated passphrases of at least 128 characters.
- Do not impose composition rules that encourage predictable patterns.
- Block known-compromised passwords if an approved local/offline or privacy-preserving check is available.
- Never log a password or include it in validation telemetry.

### 4.2 Sign-in behavior

- Normalize email consistently and look up in constant-shape behavior.
- Return a generic invalid-credentials response for unknown user, wrong password, disabled user, or invalid membership.
- Rate-limit by a privacy-preserving IP key and normalized account key, with increasing cooldown and monitoring.
- Do not permanently lock accounts solely from unauthenticated attempts.
- Record successful login and meaningful security failures without storing raw credentials or excessive IP data.
- Rotate/create a new session after authentication; no pre-login session identifier is reused.

### 4.3 Bootstrap and password recovery

- The first administrator is created through an explicit one-time CLI/bootstrap command on the trusted host.
- Bootstrap accepts secrets through secure interactive input or a mounted secret, not a command argument retained in shell history.
- Bootstrap refuses to overwrite an existing administrator without an explicit separate recovery command.
- Password recovery is not specified. Before production, choose either administrator-assisted reset or an email-based flow with expiring single-use tokens. No insecure security questions.

## 5. Session security

- Browser receives an opaque random token with at least 256 bits of entropy.
- Database stores only a cryptographic hash of the secret token plus a non-secret selector if required.
- Cookie attributes in production: `HttpOnly`, `Secure`, `SameSite=Lax` or stricter, path `/`, no broad parent domain. The current Shopify client-credentials flow has no browser OAuth callback; a future authorization-code onboarding flow must re-review cookie/CSRF behavior.
- Use a host-prefixed cookie name when deployment topology permits.
- Default idle timeout: 8 hours. Default absolute timeout: 7 days. Client may require stricter values.
- Update `last_seen_at` at a throttled interval, not every request.
- Revoke on logout, password reset/change according to policy, user disable, membership disable, and administrator revoke-all action.
- Server validates user/membership status and session expiry on every authenticated request.
- Redis may cache a session lookup briefly but cannot extend or resurrect a revoked database session.
- Never place session tokens in URLs, local storage, frontend logs, analytics, or error reports.

## 6. CSRF and browser security

- Unsafe cookie-authenticated methods require a CSRF token bound to the session and validation of `Origin`/`Host`.
- Webhook endpoints do not use browser sessions; they use provider authentication and separate rate limits.
- CORS allows only configured first-party origins and credentials; wildcard origins with credentials are forbidden.
- Apply a Content Security Policy with explicit `default-src`, script, style, image, connect, frame, object, and base restrictions compatible with the final Next.js build.
- Send HSTS after HTTPS deployment validation, `X-Content-Type-Options: nosniff`, an appropriate `Referrer-Policy`, and frame restrictions through CSP.
- Do not render provider/customer content as raw HTML.
- External links opened in a new tab use safe `rel` values.
- Sensitive pages use `Cache-Control: no-store`; service workers must not cache authenticated API responses.

## 7. Authorization and tenant scope

### 7.1 Enforcement

- NestJS guard resolves active session, user, membership, organization, and permissions.
- Application services receive a non-optional `OrganizationContext`.
- Database repositories require organization ID for every business lookup/mutation.
- Looking up an object by UUID never grants access; organization ownership and permission are checked.
- Frontend permission checks improve UX only; API is authoritative.
- Background jobs carry organization ID and revalidate target ownership.
- Integration webhook routing binds the signed account/shop/phone identity to one configured connection and organization.

### 7.2 Permission policy

High-consequence permissions are separate:

- Integration credential/config changes: `integrations.manage`.
- Order confirmation: `orders.confirm`.
- Shipment create/retry: `shipments.create`, `shipments.retry`.
- Message send/retry: `messages.send`, `messages.retry`.
- User changes and fixed-role assignment: `users.manage`.
- Audit access: `audit.read`.

The MVP exposes exactly two roles, `ADMIN` and `OPERATOR`, with a fixed permission matrix enforced by the API. Administrators can manage users and assign those two roles, but cannot create custom roles or edit permission mappings. Additional roles and editable permission systems are post-MVP.

### 7.3 Cross-organization testing

Automated tests seed a second organization in test environments and verify that IDs, filters, export paths, timelines, jobs, messages, integration events, and audit logs cannot cross boundaries. This is required even though the deployed MVP has one organization.

## 8. Secrets and cryptographic keys

### 8.1 Secret handling

- Initial deployment injects secrets through environment variables or mounted secret files; production operators should use a managed secret store when available.
- Shopify MVP variables are `SHOPIFY_SHOP_DOMAIN`, `SHOPIFY_CLIENT_ID`, `SHOPIFY_CLIENT_SECRET`, and `SHOPIFY_API_VERSION=2026-07`. The backend exchanges the first three as client credentials, caches the 24-hour access token server-side, and renews it automatically.
- Shopify client secrets and access tokens are never logged, committed, placed in browser code, or returned by the API. The frontend receives only configured/not-configured state, health, last synchronization, and safe errors.
- Next.js public environment variables must never contain provider secrets, database/Redis credentials, session keys, or encryption keys.
- API responses expose configured/not-configured, safe account identifier, last validation, and optional token expiry only.
- Secret changes are write-only and audited as “secret rotated/updated,” never with values.
- Do not persist credentials inside BullMQ job payloads, outbox payloads, audit metadata, or exception objects.
- Provider clients resolve credentials at execution time from server-side configuration/secret storage.

### 8.2 Encryption

- All external and internal network traffic uses TLS in production; database/Redis TLS is required when traffic leaves a trusted single-host private network.
- The MVP minimizes customer data and restricts access. Per-field customer-data encryption is deferred until required before broader commercial deployment; if introduced, it must use authenticated application-level encryption and managed key rotation.
- Use a versioned envelope containing algorithm/key version/nonce/ciphertext/tag.
- Keys are independent from database backups and support rotation by key version.
- Searchable exact phone/email uses a keyed HMAC normalization index, not deterministic plaintext encryption.
- Password hashes are hashing, not encryption.
- Backups are encrypted with a key separated from the backup data.

Cryptographic algorithms and libraries are selected from maintained platform libraries at implementation time; custom cryptography is prohibited.

## 9. Webhook security

For every provider:

1. Accept only HTTPS in production.
2. Limit method, content type, content length, and request duration.
3. Capture exact raw body bytes.
4. Verify the official signature/challenge mechanism before trusting parsed data.
5. Use constant-time comparison where the official protocol requires digest comparison.
6. Bind external account identity to an active integration connection.
7. Enforce replay/timestamp windows only when defined by the official protocol; deduplicate every stable event ID.
8. Store only verified, minimized payloads.
9. Return a generic response without internal error detail.
10. Alert on sustained invalid signatures or unknown account identities.

Shopify and WhatsApp verification must be implemented from their pinned official documentation. Ozone verification cannot be designed until its official contract is supplied.

## 10. Provider egress security

- Provider base URLs are fixed by adapter configuration and allowlisted; no arbitrary per-request host.
- Enforce DNS/connection/read timeouts and bounded response sizes.
- Validate TLS certificates; no production bypass.
- Authorization headers are constructed inside the adapter.
- Redirect following is disabled unless explicitly required and host-validated.
- Rate limits and concurrency are per connection/provider.
- Validate provider responses before mapping; unknown schema is a safe failure.
- Log provider request IDs, operation type, duration, and safe status, not full customer payloads.

## 11. Input, API, and data integrity

- Validate all REST, webhook-after-verification, job, configuration, and provider response data with explicit schemas.
- Reject unknown/oversized fields on security-sensitive endpoints where compatibility permits.
- Cap list page size, search length, date ranges, and exported row counts.
- Use Prisma parameterization. Raw SQL is isolated, parameterized, code-reviewed, and test-covered.
- Use integer minor units and validated ISO currency/country codes.
- Normalize but preserve authoritative source identifiers as strings.
- Mutations use optimistic version checks where concurrent update could lose state.
- File uploads and arbitrary URL imports are outside MVP and remain disabled.

## 12. Logging, errors, and observability

### 12.1 Mandatory redaction

Redact or omit:

- `Authorization`, cookies, session/CSRF tokens, API keys, client secrets, access tokens, webhook secrets/signatures;
- passwords and password hashes;
- full phone numbers, email addresses, names, street addresses, notes, message template parameters;
- raw webhook/request/response bodies containing PII;
- database/Redis URLs with credentials.

Use entity IDs, provider request IDs, last-four phone digits when necessary, and safe error codes. Redaction is tested with automated sentinel secrets.

### 12.2 Error handling

- Client errors contain stable safe code, human message, correlation ID, and field issues.
- Stack traces appear only in controlled server diagnostics and are still redacted.
- Provider error bodies are parsed into an allowlisted safe shape.
- Validation errors do not echo secrets.
- Authentication failures remain generic.

### 12.3 Security monitoring

Alert on:

- authentication spikes/cooldowns and disabled-account attempts;
- invalid webhook signatures and unknown provider accounts;
- repeated authorization denials;
- integration credential failures;
- abnormal shipment/message retry volume;
- queue/outbox backlog or stalled worker;
- backup/restore verification failure;
- unexpected administrative role/credential changes.

## 13. Data privacy

### 13.1 Data minimization

- Import only Shopify fields required for displayed workflows, fulfilment, communication, reconciliation, and legal operations.
- Do not treat marketing consent as WhatsApp transactional consent without approved policy.
- Do not store inbound WhatsApp message content in MVP.
- Keep order/address snapshots only because operational history and shipment require them.
- Avoid broad raw payload retention; prefer typed facts plus provider IDs/hashes.
- Restrict customer details to roles that need them.

### 13.2 Retention and deletion

Before production, the client must approve:

- customer/order/address retention;
- message status and template-parameter retention;
- webhook/raw diagnostic retention;
- audit/log retention;
- session/security telemetry retention;
- backup retention;
- handling of Shopify erasure/redaction webhooks and data subject requests.

Deletion must account for operational/legal retention and backup limitations. The product must not promise instant deletion from immutable backups without a compatible backup design.

### 13.3 Privacy operations

- Document data controller/processor roles and subprocessors.
- Provide a procedure to locate data by external customer ID and approved contact hashes.
- Audit privacy exports/deletions without recording exported personal data in the audit event.
- Restrict production database and backup access to named administrators.
- Never copy production customer data into development/test environments without approved anonymization.

## 14. Infrastructure and deployment hardening

- TLS terminates at a maintained reverse proxy/load balancer; HTTP redirects to HTTPS.
- Only web/API public ports are exposed. PostgreSQL and Redis remain private/firewalled.
- Redis requires authentication and a dedicated instance/database; dangerous administrative access is restricted.
- Containers run as non-root with read-only filesystem where feasible and a small writable temp area.
- Images use maintained pinned base images and contain no source secrets.
- Set CPU/memory/process limits and graceful shutdown for API/worker.
- Production debug endpoints, Prisma Studio, source maps containing source/secret context, and fake-provider controls are disabled/restricted.
- Health endpoints reveal no configuration or dependency credentials.
- Host OS, Docker runtime, reverse proxy, PostgreSQL, and Redis have an owner and patch schedule.
- Clock synchronization is required for sessions, signatures, event ordering, and audit.

## 15. Dependency and release security

- Commit `pnpm-lock.yaml`; CI uses frozen lockfile.
- Dependabot/Renovate-equivalent updates may be adopted after review; critical advisories have an explicit response path.
- Run static analysis, type checking, unit/integration/e2e tests, secret scanning, dependency audit, and container scan in CI.
- Generate an SBOM for production images.
- Protect release branch, require review, and record release commit/image digest.
- Pin GitHub Actions/CI dependencies by trusted immutable version where applicable.
- Do not run untrusted provider payloads as code or templates.
- License compatibility is reviewed for production dependencies.

## 16. Backup, recovery, and availability

- Document a basic encrypted PostgreSQL backup procedure for the controlled client test. Automated off-host backup, restore automation, and stronger RPO/RTO commitments are required before broader commercial deployment.
- Restore drill into an isolated environment before production and on a recurring schedule.
- Back up required configuration metadata separately from secret values; document secret recovery/rotation.
- Redis is not the sole copy of accepted work. After Redis loss, republish from PostgreSQL outbox/integration-operation state.
- Document release rollback: application rollback is allowed only when database compatibility is maintained; otherwise use a roll-forward migration.
- Document host-loss recovery, DNS/TLS restoration, and administrator bootstrap recovery.

## 17. Incident response

Minimum runbook:

1. Identify severity, affected organization/data/provider, and correlation window.
2. Preserve relevant redacted logs/audit evidence.
3. Contain by revoking sessions/credentials, disabling a connection, or stopping a queue without deleting durable state.
4. Rotate exposed secrets and invalidate dependent sessions/tokens.
5. Reconcile orders, messages, and shipments before resuming external effects.
6. Restore from verified backup only when integrity requires it.
7. Notify client, providers, and authorities according to contract/law.
8. Record timeline, root cause, impact, remediation, and follow-up tests.

Provider-specific emergency controls should pause message sending, courier creation, or Shopify outbound fulfilment independently while preserving inbound durable events.

## 18. Security verification checklist

Release cannot pass unless:

- Argon2id parameters are benchmarked and recorded.
- Session cookie, revocation, idle/absolute expiry, and fixation tests pass.
- CSRF and Origin tests pass for every unsafe browser route.
- Permission matrix and cross-organization negative tests pass.
- Webhook valid/invalid/tampered/replayed tests pass for implemented providers.
- Logs pass automated secret/PII sentinel scans.
- Dependency, container, and secret scans have no unresolved critical finding.
- Production images run as non-root and fake-provider controls follow environment policy.
- Database and Redis are not publicly reachable.
- Backup restoration succeeds and recovered outbox/inbox work is reconciled.
- Security headers and TLS configuration are verified.
- Ozone live mode remains disabled until official authentication/webhook rules are implemented and reviewed.

## 19. Unresolved security/privacy inputs

- Hosting environment, jurisdiction/data residency, public domain, and TLS owner.
- Approved secret manager/key storage and rotation frequency.
- Password recovery and MFA requirement. MFA is recommended for administrators but is not specified in MVP scope.
- Data retention, deletion, audit retention, and backup retention.
- WhatsApp consent/legal basis and customer-facing privacy notices.
- Shopify privacy/compliance obligations for the app's actual distribution type.
- Ozone credential, webhook, and data-security contract.
- Incident contacts, notification deadlines, monitoring/log destination, and production access list.
